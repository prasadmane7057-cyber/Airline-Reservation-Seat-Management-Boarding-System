Subject 1

PSOOP concepts organize airline entities as objects with state and behavior. Java is the clearest explicit course demonstration in this repository. The web backend also separates its responsibilities into modules, but it is JavaScript rather than a reuse of these Java classes.

What a demonstration proves

The Java practicals show object-oriented modeling, method dispatch, booking-state behavior, exception paths, validation, and a local file format. They do not prove Java persistence is synchronized with the MySQL-backed web API.

Subject 2

PL — Programming Lab / Data Structures

The C++ practicals choose a data structure to match an airline operation. These implementations make the abstract structures tangible by inserting passengers, mapping seats, promoting waitlisted passengers, ordering manifests, or undoing seat selections.

Concept / structureAirline use and behaviorProject location
Fixed array and sequential searchA bounded passenger register supports add, display, lookup, update, and delete by PNR. Lookup scans entries linearly; deletion shifts later entries to close the gap. Capacity is limited to 50 entries.cpp-ds/src/PassengerArray.h; PassengerArray.cpp
Two-dimensional arrayRows and columns represent cabin seats. Values encode available (0), booked (1), or blocked/emergency (2); bounds are checked, and rows map to cabin classes.cpp-ds/src/SeatMap2D.h; SeatMap2D.cpp
Sparse representationThe full cabin grid is dense, but an auxiliary vector records only non-available seats. It illustrates the sparse-matrix idea when most seats are empty.cpp-ds/src/SeatMap2D.h (occupiedList); SeatMap2D.cpp
FIFO queue / waitlistPassengers join a waiting line in arrival order. When a booked passenger cancels, their seat is released and the queue front is promoted first, preserving fairness by arrival order.cpp-ds/src/Waitlist.h; Waitlist.cpp (std::queue<Passenger>)
Circular queueThe boarding line uses a fixed array; front/rear wrap using modulo, reusing freed slots without shifting the remaining passengers. An explicit count distinguishes full from empty.cpp-ds/src/BoardingQueueCircular.cpp (enqueue, dequeue, display)
Singly linked listBooking-history nodes link to the next booking; records can be appended, searched by PNR, and displayed. The destructor releases the allocated nodes.cpp-ds/src/LinkedList.cpp (BookingHistoryList)
Doubly linked list and sorted mergePassenger manifest nodes hold previous and next pointers; seat ordering enables inserting records into a sorted list and merging boarding-group manifests.cpp-ds/src/ManifestMergeDLL.cpp
Stack / LIFOEach seat select/cancel action is pushed. Undo pops the latest action and applies its inverse, so the most recent change is reversed first.cpp-ds/src/undostack.cpp
Composition of structuresThe combined demonstration invokes passenger storage, a seat map, and a waitlist as separate components of one console scenario.cpp-ds/src/main.cpp; PassengerArray.cpp; SeatMap2D.cpp; Waitlist.cpp

How to explain the data-structure choices

  • Array: simple indexed seat/passenger storage with fixed capacity; linear search is straightforward but grows with the number of stored entries.
  • Queue: natural for fairness and first-come-first-served service at a waitlist or boarding gate.
  • Stack: natural for undo because the newest action is the first one reversed.
  • Linked list: supports dynamically linked records and ordered insertion, at the cost of pointer management and traversal to find positions.
  • 2D / sparse seat map: the grid mirrors cabin coordinates; sparse tracking avoids listing every available seat when reporting exceptions/status.
Boundary: these C++ structures are coursework implementations and demonstrations. The website uses MySQL tables and backend logic for live booking; the C++ arrays and queues are not the production storage layer and do not automatically synchronize with it.
Subject 3

COA — Computer Organization and Architecture

COA examples connect high-level airline arithmetic to machine-level representation and execution: values are loaded into registers, operations update register contents, memory holds input/output data, and control flow responds to comparisons.

ConceptHow the project demonstrates itProject location
Registers and arithmetic instructionsThe fare practical loads base fare into RAX, tax into RBX, discount into RCX, then performs ADD and SUB; the result is stored and printed. Example: 5000 + 900 − 500 = 5400.assembly-component/fare_calc.asm; C++ companion fare_calc_sim.cpp
Memory sections and data sizesNASM separates initialized constants/data, reserved storage, and executable instructions using .data/.bss/.text. Directives such as dq and resq reserve 64-bit quantities.assembly-component/fare_calc.asm; coa-nasm/HexToBCD.asm; coa-nasm/out/model/fuelcalci.asm
Addressing and memory accessExamples load and store values through registers and memory operands, including RIP-relative references such as [rel base_fare].assembly-component/fare_calc.asm; coa-nasm/HexToBCD.asm
Input/output calling conventionAssembly routines call C runtime printf/scanf. Register arguments and stack space/alignment demonstrate the platform ABI boundary.assembly-component/fare_calc.asm (SysV-style registers); coa-nasm/HexToBCD.asm and fuelcalci.asm (Windows x64 shadow-space setup)
Multiplication, division, and conditional branchThe fuel example multiplies distance by fuel rate, adds reserve, subtracts from capacity, then compares remaining fuel and branches to a critical/low/sufficient status message.coa-nasm/out/model/fuelcalci.asm (assembled by the root PowerShell runner)
Number systems and BCDA 64-bit hexadecimal booking-like value is converted to decimal digits and packed BCD for display, illustrating base conversion and digit representation.coa-nasm/HexToBCD.asm
Control unit: fetch/decode/executeA small instruction list is fetched in sequence, its opcode is decoded, and a stub ALU executes ADD/SUB/MUL. This is a conceptual CPU control-flow simulation, not a hardware emulator.java-oop-coa-ui/src/coa/controlunit.java
Higher-level arithmetic modelA Java fare calculator applies cabin multipliers and a passenger-count surcharge, presenting the same business domain above the assembly level.java-oop-coa-ui/src/coa/FareCalculator.java

Where COA meets the airline domain

Fare/tax/discount and fuel/distance arithmetic provide meaningful values for the examples. They are independent practicals: the NASM fare result is not the live backend’s fare calculator. The web booking backend separately calculates a fare breakdown in airline-backend/src/utils/fareCalculator.js.

The root run_integrated_system.ps1 assembles the Windows examples with NASM and links them with GCC. Linux ELF practicals run only if Debian on WSL is available; the runner reports when those are skipped.

Subject 4

CGL — Computer Graphics Lab

CGL turns routes, airport nodes, aircraft silhouettes, and cabin seats into pixels and filled shapes. The project shows both algorithmic output and interactive renderings.

How the graphics concepts relate to the booking experience

A route drawing corresponds visually to a flight between airports; clipping keeps only the part of a route inside the chosen viewing window; texture and light/material effects make the aircraft shell read as a metal surface; a seat grid corresponds to cabin layout; fill colors correspond to seat status. These are illustrative representations. The C++/OpenGL visuals do not query live seat inventory or render the Vue seat-selection page.

Validation note: the integration runner compile-checks CG source files and opens the standalone HTML visualizer. OpenGL window builds require the appropriate FreeGLUT/OpenGL development environment.

One booking, viewed across subjects

  1. PSOOP: Passenger, Flight, Seat, and Booking model the domain and its behavior.
  2. PL: arrays/maps/queues/lists/stacks demonstrate passenger records, seat occupancy, waitlisting, manifests, and undo.
  3. COA: fare arithmetic is reduced to register operations; values are stored and processed at machine level.
  4. CGL: the route and cabin are rendered as geometric shapes and rasterized pixels.
  5. Web application: a real UI workflow sends a booking request to an API and, when MySQL is configured, persists associated records transactionally.
Keep the boundaries clear in a presentation: the connection among subjects is a shared airline scenario and complementary demonstrations. Unless specifically wired otherwise, the Java, C++, assembly, and browser visualizer examples do not invoke one another or the live web API.
